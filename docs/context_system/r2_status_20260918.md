## 3. 与 mini 不同且已处理的地方

1. 两者都缓存已计算的输出 KV；SGLang 还发布未完成 chunk，必须限制在有 Drop 证明的终态前缀，
   不能把未计算的最后 sampled token 或临时 occurrence 放入树。
2. Unified insert 会释放重复输入页，且稀疏恢复可使借用/私有页交错，不能沿用单个保护长度；
   使用 CPU 所有权 mask 和 source lease。P/D 使用同一算法，不要求缓存内容相同。
3. 原生 SWA 独立池回收行为与 mini 不同，R2 用共享全层池对齐；不关闭 SWA attention。
4. mini 的部分 masked/mixed/graph 限制不移植到 SGLang；保留其调度能力并隔离请求元数据。
5. 原生 chat 模板、语法约束及采样不同。固定 token 数值测试对齐输入 IDs、模板日期、
   Retry/连续 Repos 的缓存路径；完整吞吐使用各自实际生成历史，因此不声称全轨迹输入完全相同。
6. 原生 P unfinished-cache 去重可用 canonical 页替换重算页，普通/PD 热路径因此可能不同；
   按真实交接路径比较，不为实现差异放宽冻结误差阈值。

## 7. 原生 PD 超时：现有实验能定位到哪里

### 7.1 三类问题必须分开

1. **描述符队列满：已修复。** Drop/COW碎片可跨层放大地址区间数；1024分批后真实字节
   校验及旧PD C1完整轨迹通过。它与仅72区间/288MiB的原生冷请求超时不同。
2. **原生TCP传输执行中的CUDA等待：已直接观察并复现触发条件，尚未修复。**
   原生C2第一次44成功/4失败但无明确timeout日志，原因未判；加分批保护后第二次126成功/
   2失败，仍无效。单条70407-token冷前缀进一步复现30.302871s的显式timeout。
3. **NVLink长尾：仍未定位。** 成功C2无超时，但case228 turn18从P完成标记到D ready
   **81.301s**；P完成→发送队列时间戳13.163s，最终传输尾段69.164s。阶段有重叠，不能相加，
   也不能将81s全部叫纯字节搬运。不是D已经ready却排队81s；它发生在D ready之前。

- 93.324503s：主线程 `cudaMemcpyAsync` 开始，API约12.797724s才返回。
  对应32KiB pageable D2H直到106.122197s执行，GPU搬运本身约 **3.040µs**。
- 93.324546s：I/O线程 `cudaMemcpy` 开始，内嵌 `pthread_rwlock_wrlock` 等待
  **12.797681s**；对应64KiB GPU D2H约 **4.832µs**。
- OSRT栈：`libc → libcuda580.178.04 → cuMemcpy → cudaMemcpy →
  mooncake::ClientSession::writeBody → asio`。此间P forward kernels仍在执行。
- 类似约12秒的锁等待反复出现，可让一个288MiB batch经历约25秒等待；早段还观察到
  scheduler `cudaLaunchKernel` 在驱动读锁上等待约12.05秒。

所以“已经提交传输，GPU→CPU staging / CUDA驱动推进被计算相关依赖和锁竞争拖住”
有直接证据；不是单纯网卡需要30秒发送这些字节。调度stream依赖可以参与形成条件，
但这次30秒计时发生在Mooncake worker已调用engine之后，不能解释成worker尚未被调度。
原生 `prefill.py:768` 等待 `copy_done`，`:1572` 转页号；
`mem_cache/common.py:42` 的 `kv_to_page_indices` 包含 `.cpu().numpy()`，
`scheduler.py:1906` 有WAR stream依赖。这些是相关读回路径，**Nsight没有Python栈证明
上述32KiB恰好来自哪一行**，不能把候选调用认定为唯一根因。

Mooncake v0.3.13 TCP的64KiB普通host staging与同步CUDA拷贝位于I/O回调链，
不是所有“Async”调用都保证host不阻塞；CUDA明确允许内部资源争用造成阻塞。
来源：[Mooncake TCP实现](https://github.com/kvcache-ai/Mooncake/blob/v0.3.13/mooncake-transfer-engine/src/transport/tcp_transport/tcp_transport_session_impl.h)、
[CUDA13 API同步语义](https://docs.nvidia.com/cuda/archive/13.0.0/cuda-runtime-api/api-sync-behavior.html)。
不能仅凭legacy default stream推断它隐式等待所有计算：这里Torch池流是nonblocking。
engine同步调用释放GIL，也不支持“Python GIL锁住全部传输”的解释。

### 7.4 小型反事实实验与尚未解决的反例

同卡约1.42s GPU计算、32KiB元数据读回、另线程独立64KiB CUDA拷贝，三模式各3次：
仅计算0.166–0.322ms；加入pageable读回1.366–1.369s；pinned异步读回0.129–0.148ms。
9/9数据精确，Nsight仅pageable组捕获约1.366s驱动写锁等待。
这证明pageable读回能干扰无关通信copy，不能外推为完整engine只改pinned即可修复。

直接Mooncake TCP双GPU实验将计算加长到约35.6s，保持72×4MiB=288MiB：

| 条件 | host读回调用s | engine耗时s | 返回码 |
| --- | ---: | ---: | ---: |
| 仅计算 | 0.000038 | 0.210088 | 0 |
| pageable读回 | 35.604863 | 30.302957 | -1 |
| pinned异步读回 | 0.000174 | 30.302748 | -1 |

第三组是必须保留的反例：CPU copy已快速返回，engine仍超时；说明小copy探针不足以
覆盖完整TCP pipeline，还可能有copy engine/stream、设备同步或engine后续进度依赖。
这些候选尚无本组Nsight来区分，不能指定其中一个为已证明原因。三组在等待计算和晚到
传输结束后payload均相同，**晚到正确不代表超时请求成功，也提示失败清理必须保护在途页**。
每组deadline约30s+301989888ns，pageable组稳定复现与真实batch相同的30.303s超时。

### 7.5 证据边界

- TCP v2模型profile及小copy因果profile有完整GPU记录。no-overlap与NVLink模型profile
  在退出时未完整flush，分别缺kernel或同时缺kernel/memcpy表；保留CPU/OSRT及独立传输日志。
  **缺失轨迹不是GPU空闲。** 没有据此画完整NVLink GPU利用率。
- Nsight配置 `--sample=none --cpuctxsw=none`；这里CPU时间线是API/OSRT，不是CPU利用率采样。
- 环境A80080GB、系统驱动535.161.08、进程兼容libcuda580.178.04、Torch2.13cu130、
  Mooncake0.3.13、Nsight2025.6.1。尚未做驱动版本对照，不能认定驱动版本本身有bug。
- NVLink仅同机；没有RDMA/跨主机通过结论，也没有证据表明D Radix本身能消除冷请求超时。

## 8. 效率风险与未完成项

已经避免的热点：逐token全树扫描、GPU页号读回用于容量去重、每消息重复完整模板渲染、
所有历史版本永久保留、连续R无条件冷算、所有无功能请求进入Context计算分支。
按需当前chunk规划、紧凑IR、CPU生命周期元数据、对齐打包、来源租约与延迟终态副本
都有定向验证；**尚无证据证明每个实现函数已经全局最优**。

仍重点关注：共享Full/SWA池额外KV量；mask/SWA metadata规划和JIT；低容量下Retry/COW峰值；
稀疏传输fragment数量及1024批间等待；D-cache bitmap和COW成本；CPU读回/同步与通信推进干扰。
drop-skipped只统计本次初始物理驻留但所有query均未读的Drop KV，不含已释放hole或SWA自然裁剪。

未完成门槛：新版D-cache ON/NVLink的C1/C2原生↔修改版none/Drop完整配对；
NVLink81s长尾归因；原生TCP超时的生产级修复与回归；最新路径更广压力稳定性。
固定路径误差通过与完整输出结构正常，不等于任意Agentic答案质量保证或自由生成逐字等价。
目前不能把“除了传输超时之外全部完成”作为结论。

若用户决定继续，建议先区分两条工作线：同机NVLink下定位81s就绪前长尾并补齐必要吞吐
配对；TCP另做最小engine/stream推进诊断，再选择修复方案。暂不修改全局scheduler策略、
不直接延长timeout，也不把pinned copy单点改动当成已验证方案。以上仅建议，本轮未执行。
